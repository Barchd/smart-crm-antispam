# План разработки

Рабочий план по `SOLUTION.md`. Архитектурные решения здесь не обсуждаются — только порядок сборки, готовность, зависимости и приоритеты.

## Как пользоваться

- фазы идут в порядке сборки, каждая опирается на предыдущие
- у каждой фазы есть идентификатор `P0`–`P11`
- перед началом фазы пишется спека в `specs/PNN-<slug>.md`
- чекбоксы отмечаются по факту, а не заранее
- ссылки вида `§7.2` указывают на разделы `SOLUTION.md`

## Структура проекта

```
crmtest/
  config/              # настройки Django, urls, api
  crm/                 # пользователи, клиенты, сделки, воронка, журнал, UI
  intake/              # приём заявок, статусная машина, риск, воркер
  ai/                  # клиент Ollama, схема, промпт, fallback
  bot/                 # админский Telegram-бот
  templates/
  specs/               # спеки по фазам, пишутся до кода
  docs/                # документация, пишется после кода
  chatbot_context/     # уже собранная база знаний по сайту
  SOLUTION.md
  PLAN.md
  README.md
  .env.example
  manage.py
```

Модулей четыре, как в §4. Пользователь живёт в `crm`, отдельного приложения под аутентификацию нет.

## Документация

Правило: **фаза не считается закрытой, пока не написана документация по её коду.** Документация — не отдельная фаза в конце, а часть готовности каждой фазы.

Причина: к P11 детали десяти фаз уже не вспомнить, а описывать код по памяти — это как раз тот случай, когда документация расходится с реальностью. И на защите вопрос «почему здесь так» задают по конкретному месту, а не по README.

### Что где живёт

```
docs/
  decisions.md         # журнал решений: что и почему решено по ходу
  changelog.md         # что появилось в каждой фазе
  crm.md               # модели, права, интерфейс
  intake.md            # приём, статусная машина, риск, воркер
  ai.md                # промпт, схема, валидация, fallback
  bot.md               # команды, ограничение доступа, алерты
  api.md               # эндпоинты, аутентификация, коды ответов
```

Разделение со `specs/` и `SOLUTION.md`:

| Файл | Когда пишется | Что отвечает |
|---|---|---|
| `SOLUTION.md` | до всего | какая архитектура и почему |
| `specs/PNN-*.md` | до фазы | что именно писать в этой фазе |
| `docs/*.md` | после фазы | как это работает в написанном коде |

Спека — это замысел, документация — факт. Расхождение между ними и есть самое ценное, что стоит записать: оно означает, что при реализации выяснилось что-то, чего не было видно при планировании.

### Три уровня

**В коде.** Docstring модуля в начале каждого нового файла: за что отвечает и с чем связан. Docstring функции — только там, где логика неочевидна: нормализация телефона, расчёт баллов риска, атомарный захват заявки воркером. Тривиальные CRUD-view не комментируются.

**Модульная документация.** По одному файлу на модуль. Схема данных, поток управления, точки расширения, ограничения. Пишется приростом: фаза дописывает свой раздел, а не переписывает файл заново.

**Журнал решений.** Каждое решение, принятое при написании кода и не описанное в `SOLUTION.md`, попадает в `docs/decisions.md` в формате: контекст, решение, альтернатива, последствие. Сюда же — отклонения от `SOLUTION.md` с причиной. Это главный источник ответов на защите.

### Правило по расхождениям

Если при реализации выяснилось, что `SOLUTION.md` описывает нерабочее решение, порядок такой:

1. поправить код так, как правильно
2. записать в `docs/decisions.md`, что и почему изменилось
3. поправить `SOLUTION.md`, чтобы он не врал

Пропуск третьего шага — самая частая причина, по которой документация проекта перестаёт быть полезной.

## Приоритеты и сокращения

План intentionally разбит на фазы, чтобы можно было:

- двигаться сверху вниз без архитектурных развилок
- в любой момент остановиться на рабочем состоянии
- понимать, что можно урезать без потери обязательных требований ТЗ

Что сокращать в первую очередь:

- `P4`: оформление интерфейса, канбан, визуальные улучшения
- `P7`: поиск по базе знаний и улучшение качества черновика ответа
- `P9`: дополнительные команды бота и inline-подтверждения

Что нельзя сокращать:

- `P3` целиком и тесты прав доступа
- `P5` и `P8` как основу intake и повторной обработки
- `docs/decisions.md`, потому что по нему потом отвечать на защите
